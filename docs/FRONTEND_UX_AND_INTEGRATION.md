# Frontend: UX и интеграция с backend

## Цель интерфейса

Пользователь должен за 2–3 действия ответить на три вопроса: где горит сейчас,
какие очаги относятся к одному событию и какая подтверждённая площадь/тяжесть
ущерба уже видна. Основной экран — карта; таблицы и графики вторичны.

## Макет основного экрана

```text
┌──────────────────────┬──────────────────────────────────────────────┐
│ Панель управления    │                      Карта                    │
│                      │  • очаги FIRMS                               │
│ [Дата / период]      │  ○ центры событий                             │
│ [Поиск региона]      │  ▧ гарь                                      │
│ [Обновить]           │  ▨ тяжесть / лесной ущерб                    │
│                      │                                              │
│ Слои                 │        ┌─ карточка выбранного события ─┐     │
│ ☑ Активные очаги     │        │ время, FRP, площадь, действия  │     │
│ ☑ События             │        └────────────────────────────────┘     │
│ ☐ Гарь 300 м         │                                              │
│ ☐ dNBR               │                                              │
│ ☐ Лесной ущерб       │                                              │
└──────────────────────┴──────────────────────────────────────────────┘
```

Для MVP достаточно MapLibre GL / Leaflet. Источники и слои карты должны быть
раздельными GeoJSON-source: `hotspots`, `events`, `burnedAreas`, `severity`,
`forestImpact`.

## Пользовательский сценарий

1. При открытии фронт показывает карту региона и запрашивает `hotspots` и
   `fire-events` за последние сутки.
2. Пользователь кликает на событие: открывается карточка с FIRMS-метриками и
   кнопкой «Показать гарь».
3. Кнопка подставляет `properties.bbox` события в запрос `burned-areas`.
4. В карточке гари доступны «Рассчитать изменения dNBR» и «Оценить лес в зоне dNBR».
5. Для dNBR пользователь выбирает дату до и после пожара; те же даты используются
для лесного ущерба. Результаты появляются отдельными слоями и в
   карточке.

Не запускайте dNBR и WorldCover автоматически при каждом движении карты:
это более тяжёлые запросы. Их следует запускать явным действием пользователя.

## Сопоставление UI и API

| Действие UI | Вызов | Как отобразить |
| --- | --- | --- |
| Обновить очаги | `GET /hotspots` | Круги: цвет по confidence, размер по FRP |
| Построить события | `GET /fire-events` | Кластеры/точки, popup с числом hotspots |
| Показать гарь | `GET /burned-areas` | Полигон янтарного цвета, opacity 0.4 |
| Рассчитать изменения dNBR | `GET /severity/dnbr` | `low` — жёлтый, `moderate` — оранжевый, `high` — красный; спектральные изменения, а не самостоятельный подтверждённый контур |
| Лесной ущерб | `GET /forest-impact?before_date=…&after_date=…` | Только лесная часть той же dNBR-геометрии с `forest_burned_ha` и итогом в карточке |
| Статус SAFE | `GET /safe/status` | Неактивная кнопка с подсказкой, пока `ready=false` |

Все вызовы используют префикс `/api/v1`. В development можно направлять
frontend-proxy на `http://127.0.0.1:8000`; в production API-base-url должен
настраиваться переменной окружения фронтенда.

## Состояния, ошибки и производительность

- Для каждого слоя нужны состояния `idle`, `loading`, `ready`, `empty`,
  `error` — не один глобальный spinner.
- При `200` и пустом `features` показать «Данные за выбранный период не
  найдены», а не сообщение об ошибке.
- При `422` показать текст о неверной области или датах; при `502/503` —
  «Внешний источник временно недоступен» и кнопку повторить.
- Отменять запрос при изменении bbox/даты через `AbortController`.
- Кэшировать ответы по ключу endpoint + bbox + параметры в памяти клиента;
  не хранить секреты и OAuth-токены во frontend.
- Ограничивать bbox через выбор события или инструмент рисования небольшой
  области: WorldCover и dNBR имеют серверные лимиты на размер запроса.

## Карточка события

Показывать: время первого и последнего наблюдения, число очагов, максимальный
FRP, источники, bbox, зону спутниковых наблюдений, подтверждённую площадь гари, площадь леса и площадь
каждого класса тяжести. Числа с геоданными должны сопровождаться подсказкой:
«Гарь Copernicus — продукт 300 м; это оценка, не юридически точная граница».

## Типы данных frontend

Клиенту не нужно преобразовывать геометрию: backend уже возвращает стандартный
GeoJSON. Достаточно типизировать `FeatureCollection` и читать значения из
`feature.properties`. Координаты всегда идут в порядке `[longitude, latitude]`.
