# Задача: ускорить получение VIIRS NRT-снимков для realtime AF-детекции

## Контекст

В проекте решается AF-задача: сегментация активного огня по данным спутника
VIIRS.

Для получения свежих данных используется NASA LANCE/LAADS NRT:

- наблюдения: `VJ102IMG_NRT` — NOAA-20 VIIRS I1–I5;
- геопривязка: `VJ103IMG_NRT` — latitude/longitude, solar zenith и sensor
  zenith;
- авторизация: переменная `NASA_LAADS_TOKEN` в `.env`.

Уже реализованы:

- `scripts/probe_lance_viirs_nrt.py` — поиск свежей гранулы и загрузка пары
  файлов;
- `scripts/convert_lance_viirs_nrt.py` — конвертация пары в GeoTIFF-чип
  `256×256` с GSD `375 м`, совместимый с AF-пайплайном.

Одна пара гранул занимает примерно `300–500 МБ`. Сама модель работает быстро;
главная задержка — загрузка полной гранулы. Нужен сервисный слой, который
устраняет повторные загрузки и даёт приложению прозрачный статус фоновой
операции.

## Цель

Сделать получение и локальное хранение NRT-сцен пригодным для приложения:

- повторный запрос к уже скачанной сцене должен отрабатывать за секунды;
- одна гранула не должна скачиваться одновременно несколькими запросами;
- загрузка должна переживать обрывы, частичные файлы и временные ошибки NASA;
- приложение должно получать статус `ищем сцену → загружаем → обрабатываем →
  готово / ошибка`.

Не нужно менять U-Net, обучать модель или реализовывать веб-интерфейс. Область
работы — поиск, скачивание, кэширование и возврат путей к исходным NRT-файлам.

## Исходная реализация

Текущий загрузчик уже умеет:

- искать последнюю сцену по bbox и временному окну;
- скачивать `VJ102IMG_NRT` и соответствующий `VJ103IMG_NRT`;
- передавать токен через HTTP-заголовок;
- отличать NetCDF от HTML-страницы авторизации;
- проверять размер скачанного файла.

Тяжёлые данные хранить вне репозитория, например:

```text
E:\ForestFire\lance_nrt_cache\
```

Ни `.nc`, ни токены, ни `.env` в Git добавлять нельзя.

## 1. Переиспользуемый модуль

Вынести логику в модуль, например `ml/realtime_nrt.py`. CLI-скрипт можно
сохранить, но он должен использовать эту общую реализацию, а не дублировать
код.

Ожидаемый интерфейс:

```python
scene = get_latest_viirs_scene(
    bbox=(west, south, east, north),
    token=token,
    cache_dir=Path(r"E:\ForestFire\lance_nrt_cache"),
)

print(scene.status)
print(scene.acq_datetime)
print(scene.image_path)  # VJ102IMG_NRT
print(scene.geo_path)    # VJ103IMG_NRT
print(scene.cache_hit)
```

Возвращаемый dataclass либо словарь должен содержать:

- `status`: `ready`, `downloading`, `not_found` или `error`;
- `acq_datetime`;
- `product`;
- `granule_id`;
- `image_path`;
- `geo_path`;
- `cache_hit`;
- `message`;
- техническую причину при ошибке;
- тайминги выполнения.

## 2. Дисковый кэш

Ключ кэша — идентификатор гранулы, а не bbox: одна сцена покрывает большую
полосу, поэтому может использоваться многими запросами.

Пример структуры:

```text
E:\ForestFire\lance_nrt_cache\
  VJ102IMG_NRT.A2026262.0418.021\
    VJ102IMG_NRT.A2026262.0418.021.nc
    VJ103IMG_NRT.A2026262.0418.021.nc
    manifest.json
```

`manifest.json` должен содержать минимум:

```json
{
  "granule_id": "VJ102IMG_NRT.A2026262.0418.021",
  "product": "NOAA-20 VIIRS NRT",
  "acq_datetime_utc": "2026-09-19T04:18:00+00:00",
  "downloaded_at_utc": "...",
  "image_size_bytes": 0,
  "geo_size_bytes": 0,
  "complete": true
}
```

Правила валидности:

- использовать кэш только если существуют оба файла, их размеры ожидаемы и
  `complete=true`;
- нулевой, слишком маленький, HTML-файл или отсутствие второго файла означает
  невалидную сцену и повторную загрузку;
- не считать сцену готовой до завершения и проверки обоих файлов.

## 3. Частичные загрузки и параллельные запросы

Требования:

- скачивать файл сначала во временный `*.part`;
- после полной проверки атомарно переименовывать его в итоговый `.nc`;
- повторно не скачивать валидный существующий файл;
- поставить lock на идентификатор гранулы, чтобы два запроса не скачивали
  одновременно одни и те же сотни мегабайт.

Допустимая схема lock-файла:

```text
VJ102IMG_NRT.A2026262.0418.021.lock
```

Нужен механизм протухания lock-файла: если процесс аварийно завершился,
следующий запрос после разумного timeout должен иметь возможность продолжить
загрузку.

## 4. Повторы, таймауты и ошибки

Добавить:

- connect/read timeout;
- 2–3 повтора с backoff для сетевых ошибок и HTTP `429`/`5xx`;
- отдельные понятные ошибки для:
  - невалидного токена (`401`/`403`);
  - отсутствия подходящей сцены;
  - сети или timeout;
  - повреждённого либо неполного файла;
  - HTML вместо NetCDF;
  - нехватки свободного места.

Токен запрещено записывать в stdout, логи, исключения и `manifest.json`.

## 5. TTL и очистка кэша

Добавить отдельную CLI-команду, например:

```powershell
python scripts\manage_nrt_cache.py `
  --cache-dir E:\ForestFire\lance_nrt_cache `
  --max-gb 30 `
  --keep-days 7
```

Логика очистки:

- не удалять сцены, которые сейчас скачиваются;
- при превышении лимита удалять сначала самые старые;
- удалять только явно определённые папки внутри `cache-dir`;
- перед удалением проверить, что итоговый путь действительно находится внутри
  заданного `cache-dir`.

## 6. Диагностика и метрики быстродействия

Возвращать или логировать диагностические тайминги без секретов:

```json
{
  "search_seconds": 0.4,
  "cache_lookup_seconds": 0.01,
  "download_image_seconds": 18.2,
  "download_geo_seconds": 15.1,
  "total_seconds": 34.0,
  "cache_hit": false
}
```

При `cache_hit=true` повторный запрос не должен обращаться к сети ради файлов и
должен завершаться почти сразу.

## Не входит в задачу

- Изменение или обучение AF-модели.
- Веб-интерфейс.
- Получение DEM, landcover и метеоданных: это отдельное продолжение работы.
- Изменение конкурсного `inference.py`, если без этого можно обойтись.
- Добавление реальных `.nc`, `.tif`, токенов или `.env` в Git.

## Допускается исследование альтернативных способов загрузки

Текущий путь через LAADS API и полные файлы `VJ102IMG_NRT`/`VJ103IMG_NRT` —
базовый, но не единственно допустимый. В рамках задачи разрешено проверять
другие официальные или технически обоснованные способы получить те же исходные
VIIRS-данные, если это может заметно сократить задержку либо объём загрузки.

Направления для исследования:

- серверный spatial subsetting: получение только нужного фрагмента сцены, а не
  полной гранулы;
- альтернативные официальные точки доступа NASA/LANCE/LAADS, включая облачное
  хранилище, если окружение и права доступа позволяют использовать его;
- кэширование гранулы на стороне сервиса и выдача локально нарезанных AOI;
- HTTP range-запросы, но только если они действительно работают с форматом и
  не приводят к скачиванию почти всего сжатого файла;
- параллельная загрузка пары наблюдений и геопривязки, если это не нарушает
  лимиты API и даёт измеримый выигрыш;
- использование готового официального сервиса подвыборки, если он сохраняет
  необходимые I1–I5, координаты и углы съёмки.

Любая альтернатива принимается только после сравнения с текущим способом на
одинаковой сцене и AOI. В отчёте нужно указать:

- источник и способ авторизации;
- какие именно данные отдаются и сохраняются ли все необходимые каналы;
- средний объём скачивания;
- время поиска, загрузки и подготовки одного чипа;
- ограничения: лимиты, доступность, стоимость, задержка появления NRT-данных;
- совместимость с `convert_lance_viirs_nrt.py` или необходимую минимальную
  адаптацию конвертера.

Нельзя заменять исходные I1–I5 данными другого сенсора либо готовыми
hotspot-точками без отдельного согласования: текущая AF-модель обучена именно
на георастровых входах VIIRS с I-каналами.

## Проверка результата

1. Выполнить первый запрос для одного bbox. Должна быть найдена сцена, скачана
   пара файлов и создан `manifest.json`.
2. Повторить идентичный запрос. Ожидаемый результат: `cache_hit=true`, пути к
   тем же файлам и отсутствие повторной загрузки.
3. Создать нулевой либо незавершённый `.part`-файл и проверить, что он не
   принимается за готовую сцену.
4. Одновременно запустить два процесса для одной гранулы. Один скачивает,
   второй ожидает или получает `downloading`, но не создаёт вторую загрузку.
5. Убедиться, что кэшированную пару принимает существующий конвертер:

```powershell
python scripts\convert_lance_viirs_nrt.py `
  --input-dir E:\ForestFire\lance_nrt_cache\<granule_id> `
  --output-dir E:\ForestFire\realtime_test `
  --af-checkpoint ml\artifacts\af_direct_strict_v1\checkpoints\best.pt
```

## Критерий готовности

Сервисный код находит свежую гранулу, безопасно сохраняет её в кэш, повторно
использует при следующих запросах и возвращает приложению прозрачный статус,
пути и тайминги. Основной выигрыш должен быть на повторных запросах: вместо
загрузки сотен мегабайт используется уже имеющаяся локальная сцена.
