# План реализации прототипа оперативного мониторинга лесных пожаров

## 1. Цель документа

Этот документ — инструкция для команды, которая будет реализовывать хакатонный прототип сервиса мониторинга лесных пожаров по спутниковым данным.

Прототип должен решать две связанные, но разные задачи:

1. Находить предполагаемые активные очаги горения по тепловым данным MODIS, VIIRS или Landsat и отсеивать часть ложных срабатываний.
2. По снимкам Sentinel-2 до и после пожара определять выгоревшую территорию, оценивать степень поражения и считать площадь в гектарах.

Результат должен быть доступен через REST API и показан на веб-карте.

Главная стратегия: сначала собрать полностью работающий вертикальный сценарий на открытых данных и простых алгоритмах, затем независимо заменять отдельные модули более точными моделями после получения полного ТЗ, датасета и метрик от организаторов.

---

## 2. Что должно получиться в MVP

Пользователь:

1. Выбирает территорию на карте или передаёт `bbox`/полигон через API.
2. Выбирает диапазон дат.
3. Получает точки предполагаемых активных пожаров.
4. Выбирает конкретный пожар.
5. Запускает анализ выгоревшей территории.
6. Получает полигон гари, общую площадь в гектарах и распределение по степени поражения.

Минимальный демонстрационный сценарий:

> Выбираем один известный исторический лесной пожар → загружаем очаги → автоматически находим подходящие снимки Sentinel-2 до и после события → строим маску гари → превращаем её в полигон → считаем площадь → показываем всё на карте.

### Обязательные результаты

- точки активных очагов с координатами, временем, источником, уверенностью и доступными характеристиками;
- объединение близких точек в пожарные события;
- контур предполагаемой гари;
- площадь гари в гектарах;
- классы поражения: `unburned`, `low`, `moderate`, `high`;
- REST API, возвращающий JSON/GeoJSON;
- интерактивная веб-карта;
- воспроизводимый демонстрационный пример на одном или нескольких исторических пожарах.

### Что не является обязательным для первой версии

- нейросеть, обученная с нуля;
- собственный полноценный алгоритм NASA-уровня для raw MODIS/VIIRS;
- обработка всей страны в реальном времени;
- микросервисная архитектура;
- мобильное приложение;
- production-grade отказоустойчивость;
- собственное долговременное хранилище всех исходных спутниковых сцен.

## 3. Входные и выходные данные

### 3.1. Пользовательский вход

```json
{
  "geometry": {
    "type": "Polygon",
    "coordinates": []
  },
  "date_from": "2026-07-01",
  "date_to": "2026-07-31"
}
```

Для упрощённого API вместо полигона можно принимать `bbox`:

```text
min_lon,min_lat,max_lon,max_lat
```

Ограничить максимальную площадь AOI в MVP, чтобы пользователь случайно не запустил тяжёлую обработку целого региона или страны.

### 3.2. Данные для поиска очагов

Первая рабочая версия использует готовые активные очаги NASA FIRMS, сформированные по MODIS/VIIRS. Обычно доступны:

- широта и долгота;
- дата и время наблюдения;
- спутник и прибор;
- brightness temperature;
- confidence;
- FRP — оценка мощности теплового излучения;
- day/night;
- дополнительные атрибуты конкретного продукта.

Важно: FIRMS — это готовый baseline, а не собственный алгоритм обнаружения пожара. Архитектура не должна связывать остальную систему с форматом FIRMS.

Возможный конкурсный вариант после уточнения требований — заменить FIRMS-адаптер детектором, который читает исходные тепловые и вспомогательные каналы VIIRS/MODIS/Landsat.

### 3.3. Данные для картирования гари

Используются сцены Sentinel-2 Level-2A:

- снимок до пожара;
- снимок после пожара;
- красный канал B04;
- ближний ИК B08 или B8A;
- коротковолновый ИК B12;
- маска качества/облаков SCL;
- метаданные сцены: дата, проекция, облачность, footprint.

Для классического NBR удобно привести нужные каналы к общей сетке, обычно к 20 м, поскольку B12 имеет разрешение 20 м. Можно ресемплировать B12 до 10 м, но это не добавит реальной пространственной детализации.

### 3.4. Выход

#### Очаг

```json
{
  "id": "hotspot-123",
  "type": "Feature",
  "geometry": {
    "type": "Point",
    "coordinates": [92.84, 56.12]
  },
  "properties": {
    "observed_at": "2026-07-15T14:32:00Z",
    "source": "VIIRS",
    "confidence": 0.91,
    "frp": 18.4,
    "status": "accepted"
  }
}
```

#### Результат анализа гари

```json
{
  "fire_id": "fire-42",
  "total_area_ha": 1247.3,
  "severity_area_ha": {
    "low": 301.2,
    "moderate": 651.4,
    "high": 294.7
  },
  "pre_image_date": "2026-07-05",
  "post_image_date": "2026-07-28",
  "method": "dnbr-baseline",
  "geometry": {
    "type": "MultiPolygon",
    "coordinates": []
  }
}
```

## 4. Архитектурный принцип

Все алгоритмически неопределённые части должны иметь стабильный интерфейс и заменяемую реализацию.

```text
DataSource
  → HotspotDetector
  → FalsePositiveFilter
  → FireEventBuilder
  → Sentinel2SceneSelector
  → BurnMapper
  → Polygonizer / AreaCalculator
  → REST API
  → Web Map
```

### Рекомендуемые интерфейсы

```python
class HotspotDetector:
    def detect(self, aoi, date_from, date_to) -> list[Hotspot]: ...

class FalsePositiveFilter:
    def filter(self, hotspots, context) -> list[Hotspot]: ...

class FireEventBuilder:
    def group(self, hotspots) -> list[FireEvent]: ...

class SceneSelector:
    def select_pre_post(self, fire_event) -> ScenePair: ...

class BurnMapper:
    def predict(self, scene_pair, aoi) -> BurnRaster: ...
```

Планируемые реализации:

| Интерфейс | MVP | Возможное улучшение |
|---|---|---|
| `HotspotDetector` | `FirmsBaselineDetector` | `RawViirsDetector`, `RawModisDetector`, `LandsatDetector` |
| `FalsePositiveFilter` | правила | XGBoost/LightGBM |
| `BurnMapper` | dNBR + пороги | U-Net или другая segmentation-модель |
| `SceneSelector` | STAC + простая оценка сцены | подбор мозаики и pixel-level cloud quality |

Такой контракт позволяет заранее реализовать API, UI, хранение результатов и dNBR pipeline, не зная окончательных конкурсных требований.

## 5. Рекомендуемый стек

### Backend и обработка

- Python 3.11+;
- FastAPI + Uvicorn;
- Pydantic;
- GeoPandas, Shapely, PyProj;
- Rasterio, GDAL, NumPy;
- Xarray/rioxarray — опционально;
- pystac-client для STAC;
- scikit-image для морфологии и polygonize-обвязки — опционально;
- scikit-learn, XGBoost или LightGBM для классификатора;
- PyTorch для U-Net;
- SQLAlchemy/GeoAlchemy2;
- PostgreSQL + PostGIS, если хватает времени;
- для совсем первого demo допустимы SQLite и GeoJSON-файлы.

### Frontend

- React + TypeScript + Vite;
- MapLibre GL JS или Leaflet;
- простая библиотека компонентов по выбору команды;
- запросы к API через `fetch` или TanStack Query.

### Инфраструктура

- Docker Compose;
- отдельные контейнеры `api`, `worker`, `db`, `web`;
- Redis + Celery/RQ/Dramatiq — только если асинхронная обработка действительно нужна;
- для хакатонного MVP вместо очереди можно использовать FastAPI background task и таблицу заданий.

### Почему не начинать с микросервисов

На старте достаточно модульного монолита. Границы задаются пакетами и интерфейсами, а не сетевыми сервисами. Спутниковая обработка всё равно будет наиболее сложной частью; распределённая инфраструктура только увеличит время интеграции.

## 7. Этап 1 — полностью работающий baseline очагов

### 7.1. Адаптер источника

Реализовать `FirmsBaselineDetector`, который:

1. Принимает AOI и диапазон дат.
2. Запрашивает MODIS/VIIRS detections.
3. Приводит разные форматы к единой модели `Hotspot`.
4. Удаляет дубликаты.
5. Сохраняет исходные атрибуты для аудита.
6. Возвращает GeoJSON.

Ключи доступа и URL хранить в переменных окружения, не коммитить в репозиторий.

### 7.2. Базовый отсев ложных срабатываний

Сделать правила конфигурируемыми, а не зашитыми в код. Возможные признаки:

- confidence источника;
- brightness temperature;
- FRP;
- день/ночь;
- вода/суша;
- лес/не лес;
- наличие нескольких близких наблюдений;
- повторное наблюдение в соседний момент времени;
- расстояние до известных постоянных промышленных источников тепла;
- локальная разница температуры между кандидатом и окружением, если доступны raw-каналы.

Для MVP достаточно нескольких понятных правил, например:

```yaml
hotspot_filter:
  min_confidence: 0.6
  min_frp: 1.0
  reject_water: true
  require_forest_intersection: false
  cluster_radius_m: 1500
  cluster_time_window_hours: 12
```

Пороговые значения в примере не считать научно утверждёнными. Их нужно подобрать на тестовых событиях и заменить после появления конкурсной методики.

### 7.3. Объединение точек в пожарные события

Отдельные спутниковые точки — не обязательно отдельные пожары. Нужен `FireEventBuilder`:

- пространственная группировка, например DBSCAN в метрической проекции;
- временное окно;
- создание общего `event_id`;
- bounding polygon/buffer для последующего поиска Sentinel-2;
- агрегаты: первая и последняя фиксация, число точек, максимальный FRP, средняя уверенность.

Не группировать координаты непосредственно в EPSG:4326 как евклидово пространство. Сначала переводить их в подходящую метрическую CRS или использовать корректную геодезическую дистанцию.

### 7.4. Definition of Done этапа

- запрос по AOI и датам возвращает очаги;
- все ответы проходят через единую доменную модель;
- фильтр можно настроить YAML-конфигом;
- близкие точки объединяются в события;
- есть минимум unit-тесты нормализации, фильтрации и группировки;
- точки и события видны на карте.

## 8. Этап 2 — выбор Sentinel-2 сцен

### 8.1. Поиск сцен

Через STAC найти Sentinel-2 L2A сцены, пересекающие AOI пожара:

- `pre`: до первой фиксации пожара;
- `post`: после последней фиксации или после разумной задержки;
- ограничение по облачности;
- достаточное покрытие AOI;
- предпочтительно минимальный временной разрыв.

### 8.2. Практическая стратегия подбора

Начальные окна:

- снимок до: от 45 до 5 дней до события;
- снимок после: от 3 до 45 дней после события;
- максимальная metadata cloud cover, например 30–40%;
- если подходящей сцены нет, расширять окно.

Это стартовые параметры, а не окончательная методика.

Оценивать нужно не только общую облачность сцены, но и облачность именно над AOI. Сцена с 60% облачности в целом может быть чистой над пожаром, а сцена с 10% — закрывать облаком нужную область.

### 8.3. Подготовка данных

Для обеих сцен:

1. Скачать только нужные assets/окна, если источник поддерживает COG range requests.
2. Обрезать по AOI с небольшим buffer.
3. Привести в одну CRS, extent, resolution и pixel grid.
4. Маскировать облака, тени облаков, снег и invalid pixels по SCL.
5. Проверить долю валидных пикселей.
6. Сохранить идентификаторы исходных сцен и все параметры обработки.

### 8.4. Риск сезонных изменений

Если снимки слишком далеко друг от друга, dNBR может реагировать не только на пожар, но и на сезон, вырубку, сельхозработы или изменение воды. Поэтому выбирать максимально близкую корректную пару и ограничивать анализ окрестностью обнаруженного события.

## 9. Этап 3 — baseline картирования гари по dNBR

### 9.1. Формулы

Для каждого снимка:

```text
NBR = (NIR - SWIR2) / (NIR + SWIR2)
```

Для пары снимков:

```text
dNBR = NBR_before - NBR_after
```

При Sentinel-2 обычно используются NIR B08/B8A и SWIR2 B12. Выбор B08 против B8A должен быть единообразным и документированным.

### 9.2. Pipeline

1. Рассчитать `NBR_before`.
2. Рассчитать `NBR_after`.
3. Рассчитать `dNBR` только на валидных пикселях.
4. Применить конфигурируемые пороги severity.
5. Удалить слишком маленькие изолированные компоненты.
6. Сделать opening/closing при необходимости.
7. Ограничить результат разумной окрестностью события или связными областями рядом с hotspots.
8. Преобразовать маску в полигоны.
9. Исправить геометрию, объединить соседние полигоны и упростить контур для карты.
10. Рассчитать площадь в равноплощадной или подходящей локальной проекции.

### 9.3. Конфигурация severity

```yaml
severity:
  method: dnbr
  thresholds:
    unburned_max: 0.10
    low_max: 0.27
    moderate_max: 0.44
    high_min: 0.44
  min_component_area_ha: 1.0
```

Значения здесь только пример структуры конфига. Итоговые пороги зависят от экосистемы, сезона, подготовки данных и методики организаторов. Сохранять версию конфига вместе с результатом анализа.

### 9.4. Площадь

Нельзя считать площадь по широте/долготе простым умножением градусов. Два допустимых подхода:

- перепроецировать маску/полигон в подходящую равноплощадную CRS и считать площадь;
- считать сумму площадей пикселей геодезически.

Перевод:

```text
hectares = square_meters / 10_000
```

Рекомендуется считать площадь по растровой маске для точности, а полигон использовать для визуализации и обмена.

### 9.5. Definition of Done этапа

- система автоматически выбирает или предлагает пару `pre/post`;
- строится dNBR raster;
- формируется маска с классами severity;
- получаются валидные GeoJSON-полигоны;
- площадь считается в гектарах;
- на карте можно переключить hotspots, контур и классы severity;
- результат воспроизводится одной командой для demo-case.

## 10. Этап 4 — REST API и фоновые задания

### 10.1. Минимальные endpoints

```text
POST /api/v1/search
GET  /api/v1/hotspots
GET  /api/v1/fires
GET  /api/v1/fires/{fire_id}
POST /api/v1/fires/{fire_id}/burn-analysis
GET  /api/v1/jobs/{job_id}
GET  /api/v1/fires/{fire_id}/burn-area
GET  /api/v1/health
```

### 10.2. Поведение

`POST /search` запускает загрузку и нормализацию hotspots.

`POST /fires/{id}/burn-analysis` не должен держать HTTP-соединение во время тяжёлой обработки. Он возвращает `202 Accepted` и `job_id`:

```json
{
  "job_id": "job-123",
  "status": "queued"
}
```

Статусы:

```text
queued → running → succeeded
                 ↘ failed
```

Для ошибки хранить безопасное пользовательское сообщение и технический лог с trace ID.

### 10.3. GeoJSON

Для географических объектов использовать GeoJSON с координатами в порядке `[longitude, latitude]`. Во внутреннем raster pipeline сохранять исходную CRS и выполнять преобразование только на границах системы.

### 10.4. Хранение

Минимальные сущности:

- `hotspots`;
- `fire_events`;
- `scene_pairs`;
- `burn_analyses`;
- `jobs`;
- `model_versions` или `pipeline_versions`.

В базе хранить геометрию и метаданные. Большие GeoTIFF/COG и модельные веса лучше хранить в объектном хранилище или локальном volume, а в базе — URI, checksum и метаданные.

## 11. Этап 5 — веб-карта

### Основной экран

- карта;
- выбор AOI рамкой/полигоном;
- диапазон дат;
- кнопка поиска;
- слои: hotspots, fire events, burn perimeter, severity;
- список найденных событий;
- панель выбранного пожара;
- кнопка запуска анализа гари;
- индикатор статуса задания;
- легенда;
- площадь в гектарах и распределение severity.

### UX демонстрации

У интерфейса должен быть заранее сохранён demo-case. На хакатоне нельзя зависеть только от живого API и удачного наличия безоблачных свежих сцен.

Предусмотреть два режима:

1. `Live`: реальный запрос к источникам.
2. `Demo`: заранее проверенный исторический пример с кэшированными результатами.

Не подменять результат незаметно. UI должен явно показывать источник данных, метод анализа, даты сцен и время обновления.

## 12. ML-часть после baseline

### 12.1. Классификатор ложных очагов

Предпочтительный первый ML-метод: XGBoost или LightGBM.

Одна строка датасета соответствует hotspot-кандидату. Возможные признаки:

- значения тепловых каналов;
- разница кандидата и локального окружения;
- статистики окна вокруг пикселя;
- NIR/SWIR и спектральные индексы;
- confidence и FRP источника, если разрешено условиями;
- день/ночь;
- месяц и локальное время;
- land/water;
- forest/non-forest;
- расстояние до промышленных объектов;
- число соседних hotspots;
- временное подтверждение соседними пролётами;
- признаки облаков и солнечного блика.

Target:

```text
1 = реальный лесной пожар
0 = ложное или нерелевантное срабатывание
```

Почему градиентный бустинг подходит:

- хорошо работает на табличных признаках;
- обучается быстрее нейросети;
- выдерживает небольшой/средний датасет;
- позволяет анализировать важность признаков и SHAP;
- легко сравнивается с набором правил.

Не использовать FIRMS confidence как скрытую замену target при заявлении собственного raw detector. Нужно заранее разделить сценарии «поверх готового продукта» и «на исходных каналах».

### 12.2. U-Net для сегментации гари

Основная перспективная ML-модель: U-Net или близкая encoder-decoder segmentation architecture.

Входные варианты:

- каналы Sentinel-2 до и после события;
- stacked tensor: `B04_pre`, `B08_pre`, `B12_pre`, `B04_post`, `B08_post`, `B12_post`;
- дополнительные `NBR_before`, `NBR_after`, `dNBR`;
- valid/cloud masks как отдельные каналы.

Выход:

- бинарная маска `burned/not burned`; или
- многоклассовая маска `unburned/low/moderate/high`.

Для первого обучения безопаснее бинарная сегментация, а severity оставить dNBR-based. Многоклассовая модель требует более надёжной и согласованной разметки.

### 12.3. Разметка и разбиение

Нужны пожарные периметры/маски, согласованные с датами снимков. Разбиение делать по событиям и географии, а не случайно по тайлам одного и того же пожара.

Правильно:

```text
train fires / validation fires / test fires
```

Неправильно:

```text
случайные соседние тайлы одного пожара одновременно в train и test
```

Иначе получится leakage и завышенные метрики.

### 12.4. Обучение U-Net

Начальная конфигурация:

- tile size 256×256 или 512×512;
- нормализация по каналам;
- encoder с ImageNet-весами допустим, но для нестандартного числа каналов потребуется адаптация первого слоя;
- loss: комбинация BCE и Dice для бинарной задачи;
- sampler, учитывающий сильный дисбаланс burned/unburned;
- аугментации: flips, rotations, умеренные radiometric transforms;
- early stopping по validation IoU/F1;
- фиксация seed и всех параметров эксперимента.

### 12.5. Порядок внедрения ML

1. Зафиксировать dNBR baseline и его метрики.
2. Подготовить версионируемый датасет.
3. Обучить простой U-Net.
4. Сравнить на одном и том же test set.
5. Добавить inference-адаптер с тем же интерфейсом `BurnMapper`.
6. Сохранить model card: данные, ограничения, метрики, версия весов.
7. Показывать в API поле `method` и версию модели.

ML-модель принимается только если она объективно лучше baseline на отложенных событиях либо даёт полезное качество там, где baseline систематически ошибается.

## 13. Оценка качества

Создать `evaluation/` с единым интерфейсом ещё до появления конкурсной разметки.

### Для детекции очагов

- precision;
- recall;
- F1;
- false positives per area/time;
- detection delay;
- метрика совпадения с допуском по расстоянию и времени.

Точный matching protocol нужно зафиксировать: какой радиус и временной допуск означают совпадение.

### Для маски гари

- IoU/Jaccard;
- Dice/F1;
- precision/recall по burned pixels;
- boundary metric при необходимости;
- ошибка площади в гектарах;
- относительная ошибка площади.

```text
area_error_ha = predicted_area_ha - true_area_ha
relative_area_error = abs(predicted - true) / true
```

### Для severity

- confusion matrix;
- macro F1;
- weighted F1;
- площадь по каждому классу;
- ordinal error, поскольку `low → high` хуже, чем `low → moderate`.

### Важное правило

Сравнивать rule baseline, dNBR и ML на одинаковом независимом наборе событий. Не подбирать пороги на test set.

## 14. Тестирование

### Unit-тесты

- преобразование входных форматов в доменные модели;
- облачная маска;
- расчёт NBR/dNBR;

- API job → результат;

### Golden demo test

Для одного небольшого исторического события сохранить:

Тест не обязан требовать точного совпадения каждого float, но должен ловить сломанные формулы, CRS и радикальные изменения площади.

## 16. Безопасность и ограничения

- секреты только в environment variables;
- ограничить площадь AOI и диапазон дат;
- ограничить число параллельных тяжёлых заданий;
- валидировать GeoJSON и даты;
- защититься от path traversal при работе с локальным кэшем;
- выставить timeout/retry для внешних источников;
- не доверять внешним метаданным и именам файлов;
- явно обозначить, что результат прототипа не является официальным сигналом для экстренных служб;
- показывать время наблюдения: спутниковый hotspot не означает непрерывное горение в текущую секунду;
- показывать облачность и качество сцены, чтобы пользователь понимал неопределённость.

## 17. Организация работы команды

### Роли

Если в команде 4–6 человек:

1. **Geo/remote sensing:** STAC, Sentinel-2, cloud masking, dNBR, CRS, polygonization.

- mock GeoJSON для frontend;
- один фиксированный demo-case.

После этого frontend может работать на mock API, geo-специалист — на локальных сценах, backend — на контракте, ML — на отдельном dataset pipeline.

## 20. Основные риски и меры

| Риск | Последствие | Мера |
|---|---|---|
| FIRMS запрещён как готовый продукт | baseline не соответствует заданию | оставить `HotspotDetector` заменяемым, готовить raw adapter |
| Нет безоблачной пары Sentinel-2 | dNBR не строится | расширение окна, мозаика, другой demo-case, quality flag |
| Ошибки co-registration | ложные границы | одна сетка/CRS/resolution и тест смещения |
| Сезонные изменения | ложная гарь | близкие даты, ограничение AOI, дополнительные индексы/ML |
| Неверная площадь | провал ключевого результата | метрическая/равноплощадная CRS и отдельные тесты |
| Leakage в ML | завышенные метрики | split по пожарам и географии |
| Медленное скачивание | demo зависает | COG window reads, cache, заранее подготовленный demo mode |
| Внешний API недоступен | нет демонстрации | кэшированный воспроизводимый сценарий |
| Команда параллельно делает несовместимые части | потеря времени | заранее зафиксированные схемы и mock API |
| Слишком ранний deep learning | нет рабочего продукта | baseline-first и строгий ML gate |

## 21. Критерии готовности прототипа

Прототип считается готовым к показу, если:

- [ ] пользователь выбирает AOI и даты;
- [ ] система получает или читает реальные hotspots;
- [ ] hotspots фильтруются и группируются в события;
- [ ] для выбранного события определяется `pre/post` scene pair;
- [ ] строится burn mask;
- [ ] контур отображается на карте;
- [ ] площадь выводится в гектарах;
- [ ] severity показана по классам;
- [ ] API возвращает валидный JSON/GeoJSON;
- [ ] интерфейс показывает даты, источник, метод и quality flags;
- [ ] есть хотя бы один заранее проверенный demo-case;
- [ ] система переживает недоступность внешнего API в demo mode;
- [ ] есть тесты NBR/dNBR, CRS, площади и GeoJSON;
- [ ] секреты отсутствуют в Git;
- [ ] все алгоритмические пороги вынесены в конфиг;
- [ ] README содержит одну команду запуска;
- [ ] команда может объяснить разницу между FIRMS baseline и собственным детектором;
- [ ] команда может показать сравнение dNBR baseline и ML, если ML уже добавлен.

## 22. Сценарий презентации

1. Коротко обозначить проблему: быстро понять, где возник пожар и сколько леса поражено.
2. На карте выбрать заранее подготовленный реальный пожар.
3. Показать входные hotspots и их временную динамику.
4. Показать, какие кандидаты были отклонены и почему.
5. Открыть пару Sentinel-2 до/после.
6. Включить слой dNBR/severity.
7. Показать полигон и площадь в гектарах.
8. Показать ответ API.
9. Объяснить модульность: FIRMS → raw detector; dNBR → U-Net.
10. Показать метрики baseline и, если готово, улучшение ML.

Не обещать «абсолютно точное обнаружение». Лучше честно показать confidence, ограничения по облакам, время спутникового пролёта и способ проверки качества.

## 23. Итоговое техническое решение

Первая версия должна быть не «одной большой нейросетью», а системой из заменяемых модулей:

```text
FIRMS MODIS/VIIRS baseline
  → rule-based false-positive filtering
  → spatiotemporal fire events
  → Sentinel-2 L2A pre/post selection
  → cloud masking and grid alignment
  → NBR/dNBR
  → severity mask
  → polygon + hectares
  → FastAPI
  → MapLibre/Leaflet web map
```

После получения полного ТЗ:

```text
FIRMS baseline → raw thermal detector / XGBoost
dNBR baseline  → U-Net segmentation
generic metrics → official hackathon protocol
generic region  → target geography and forest mask
```

Самый важный приоритет команды: сначала добиться надёжного end-to-end результата на реальном историческом пожаре. Только после этого инвестировать время в ML, масштабирование и архитектурные усложнения.
